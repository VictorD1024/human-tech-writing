# 技术文档类型

只读取并采用当前文档类型对应的部分。用户已有模板或团队规范时，以用户要求为准。

## 设计文档

按问题、约束、方案、取舍、接口或数据变化、失败方式、验证计划组织。先给推荐方案，再解释为什么；不要把所有候选方案写成同等可行。

明确区分：当前事实、设计决定、尚未验证的假设、未来计划。图表或伪代码应帮助读者理解组件关系，而不是装饰。

## README

让新读者尽快完成一次成功操作。依次说明项目用途、适用范围、前置条件、最短安装或运行步骤、预期结果和常见失败。

命令不能单独出现。命令前说明它做什么，命令后说明成功时会看到什么。不要声称“开箱即用”，直接列出依赖和限制。

## API 文档

先解释接口解决的问题，再给方法、路径、认证、请求字段、响应字段、错误条件和完整示例。

区分“必填”“可选”“缺省值”和“条件必填”。不要只写“遵循接口契约”；把约束写到字段或状态码上。

## Runbook 或操作手册

开头列出适用场景、权限和风险。步骤按可执行顺序编号，每步包含命令、预期结果和失败后的停止条件。

破坏性操作要明确影响范围和恢复方式。不要把“必要时回滚”当作完整步骤，应写明触发回滚的信号和回滚入口。

## 变更说明

回答四件事：什么变了、谁会受影响、是否需要行动、何时生效。若存在不兼容变化，放在最显眼的位置，并给迁移方法。

## 故障复盘

时间线只记录可核实事件。把直接原因、促成条件和未确认假设分开。行动项要有对象、完成条件和验证方法；材料没有负责人或日期时不要编造。

避免“加强意识”“完善机制”等无法验收的行动项。
