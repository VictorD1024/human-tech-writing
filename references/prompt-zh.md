# 可复制的中文提示词

## A：重写技术文档

```text
请把下面内容重写成技术人员能快速阅读、外行人也能跟上的技术文档。保留准确术语，但把“落盘、契约、冒烟、链路、打通、兜底”等内部黑话落实为具体对象、触发条件、动作和可观察结果。不常见缩写第一次出现时写出中英文全称，并用一句话说明它在本文中的作用；多文件内容按每个可独立打开的页面分别处理。开头说清问题、范围和读者能完成什么，正文先讲主流程和关键边界，再放参数、异常和实现细节。少用“不是 A，而是 B”“本质是”“这意味着”等制造力度的句式；只有在纠正真实误解或补充具体后果时才保留。遇到“支持、实现、保证、自动”时，写清执行者、条件、范围和可观察结果。不要为了整齐强凑三点或等长段落。区分已观察结果、推断和计划；性能结论保留指标、对照、条件和样本范围。不要改动代码块、命令、标识符、字段名、路径、链接、锚点、引用或实验数字，也不要编造接口行为、状态码、性能数据或测试结果；材料不足就明确标注待确认。
```

## B：面向跨领域读者解释

```text
请保留这份技术文档的专业精度，同时增加跨领域读者继续阅读所需的最少解释。不要把正文改成科普文章。第一次出现的陌生概念用一句就地解释；组件之间写清谁调用谁、数据往哪里走、失败时发生什么。缩写不要堆叠，必要时增加一个短词汇表。技术人员应能跳过解释直接找到接口、步骤、边界和风险，非技术读者应能看懂问题、方案和影响。不得添加材料中不存在的系统行为。
```

## C：审查 AI 句式、技术黑话和缩写

```text
请审查下面的技术文档，只列出会阻碍阅读的表达：内部黑话、歧义术语、未解释缩写、没有真实对比的“不是 A，而是 B”、只复述前文的“这意味着”，以及没有说明条件和结果的“支持、实现、保证、自动”。对每一项说明：原句、问题、缺少的具体信息和建议改写。不要因为词语听起来专业就删除；含义精确的术语只需在首次出现时解释。无法确认的缩写不要猜，也不要为了改写而补造系统行为。
```
