# Human Writing for Technical Docs

一个让 AI 把技术文档写准确、写具体，也让更多人读得懂的 Codex Skill。

它聚焦技术文档里常见的三类阅读障碍：

- “落盘、契约、冒烟、链路、兜底”这类只有团队内部默认懂的黑话
- RAG、RRF、ANN、MCP 等没有展开或连续堆叠的缩写
- “生产级、高性能、高可用、最佳实践”等没有指标和边界的技术宣传语

目标不是消灭专业术语。技术人员仍应能快速找到结论、接口、步骤和风险；相邻领域的工程师与非技术读者，则能在第一次遇到陌生概念时得到足够解释。

## 支持的文档

- 设计文档和技术方案
- README 和上手指南
- 教程和多页面技术文档
- API 文档
- Runbook 与操作手册
- 变更说明
- 故障复盘

## 安装

将仓库克隆到 Codex skills 目录：

```bash
git clone https://github.com/VictorD1024/human-writing.git ~/.codex/skills/human-writing
```

重启 Codex 或开启新会话，然后直接描述任务。也可以显式调用：

```text
使用 $human-writing 重写这份设计文档。技术人员是主读者，但请让产品经理也能看懂主流程。不要补写系统行为。
```

## 一个例子

改写前：

> 上线后先跑冒烟，确认无误再全量。中间结果定期落盘，上下游遵循稳定契约。

Skill 不会只做同义词替换，而会要求文档补齐：

- 冒烟测试具体检查哪些关键路径，怎样算通过
- 哪个组件把什么数据写到哪里，什么时候写，重启后怎样读取
- 契约的载体是什么，约束哪些字段，变更如何兼容

如果原始材料没有这些事实，Skill 会标记待确认，不会自行编造。

## 设计原则

1. **专业读者优先**：不为了通俗而牺牲精度。
2. **解释就在附近**：陌生概念第一次出现时给最少但足够的解释。
3. **术语不是禁词**：含义精确就保留，含义模糊就落实到对象和动作。
4. **不猜缩写**：无法确认全称时明确标记。
5. **不编造系统事实**：接口、字段、状态码、性能和测试结果必须来自材料。
6. **保护技术原文**：默认不改代码、命令、字段、路径、链接、引用和实验数字。
7. **页面可以独立阅读**：多文件教程在每页首次出现处解释关键缩写。
